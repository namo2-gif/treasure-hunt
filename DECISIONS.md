# Architectural & Implementation Decisions

- Used Next.js App Router with TypeScript strict mode and Tailwind CSS as standard mobile-first UI framework.
- Selected slate-900 (#0f172a) for dark background and amber-500 (#f59e0b) as the single accent color for treasure hunt aesthetic.
- Implemented `/login` and `/hq/login` with live countdown timers on receiving `THROTTLED` (showing remaining seconds).
- Middleware enforces `th_admin` JWT on `/hq/*` (redirecting to `/hq/login`) and `/api/admin/*` (returning 401 JSON), while setting `X-Robots-Tag: noindex`.
- `POST /api/admin/import` accepts CSV via multipart/form-data, JSON payload, or raw text body; validates team size (3-5), exactly 1 captain, unique student IDs, and allows re-import strictly in `setup` phase.
- Provided `002_functions.sql` migrations with server-side query fallback in `lib/event-service.ts` for atomic event actions and seamless execution.
- Designed `/hq` dashboard skeleton with 5-second polling, live clock synchronization, primary phase action dispatching, pause/resume, add-time, mode toggle, and reset controls.
- Implemented `/s/[token]` scan flow with server-side authentication redirect (`/login?next=/s/<token>`) and client mount `POST /api/scan` execution to guarantee link previews and prefetchers never register participants.
- Created QR location CRUD (`/api/admin/qr`), base64url token regeneration, and printable sheet (`/hq/qr/print`) generating 4 QR beacons per A4 page using `qrcode`.
- Mapped database-level unique constraint violations on `registrations` into strict domain error codes (`TEAMMATE_HERE`, `QR_USED_BEFORE`, `ALREADY_REGISTERED`, `QR_FULL`) for concurrent scan safety.
- Phase 4 SQL lives in `003_phase4.sql` (not appended to 002) so an already-migrated database only needs the new file. All functions are `create or replace`, safe to re-run.
- Removed the TypeScript "fallback" paths from `registerScan`, `executeEventAction` and `advanceEvent`. They duplicated Postgres logic non-atomically and could silently run when migration 002 had not been applied. A missing function now returns `RPC_ERROR` ("Something is not set up").
- `submit_answer` locks the team row before the `team_questions` row. This serialises the "is the run finished?" check so two simultaneous final answers cannot both miss each other.
- `submit_answer(kind 'r1')` returns `WRONG_PHASE` until Phase 7. `/api/state` already chooses the R1 and R3 screens, but their payloads (riddles, clue) arrive in Phases 7 and 8.
- Extra codes not in Section 8.3: `DUPLICATE_REQUEST` (a requestId already used by another team), `RPC_ERROR` (database function missing or failing). Voided question answers return `LOCKED`; an unknown question number returns `CONTENT_MISSING`.
- `player_state()` (SQL) builds the whole `/api/state` snapshot in one round trip and takes `eventNowMs` from `event_now_ms()`, never from the Node clock. `lib/state.ts` maps it to the player DTO.
- `mine` items carry a `status` (open, one_try_left, correct, locked, voided) so members see the status of their own questions. No points are ever sent.
- SQL rule: Every UPDATE and DELETE must have a WHERE clause (use `where true` if you mean all rows). Supabase rejects it otherwise. Added `where true` to `reset_event_data` and `open_round3`.
- Phase 5: Run timing, hard end, expired runs score 0, void_question, mark_absent, unmark_absent, cancel_registration implemented in Postgres functions (`supabase/migrations/004_phase5.sql`) and wrapped via server services.
- `void_question`: sets `voided = true`, creates a `score_adjustments` row with `max(0, full - already_earned)`, and re-evaluates whether the run is finished (advancing to run 2 if eligible).
- `mark_absent`: sets `absent = true`, reassigns unassigned pieces (1..N) and any pieces currently held by the absent student to `move_to` teammate with `via='admin'`. Existing registrations are kept to preserve capacity slots.
- `cancel_registration`: deletes the registration row and frees matching piece assignment held by that student, freeing up both the QR slot and piece number for another team member.
- Admin event control bug fix: Client now guarantees sending `Content-Type: application/json` and `body: JSON.stringify(payload ?? {})` with a `finally` block resetting loading states on error; route handlers safely read text and default empty bodies to `{}` while still catching malformed JSON.
- Phase 6: Content and admin interfaces use localized `HQNav` navigation across all `/hq/*` sub-routes for direct navigation without cross-component coupling.
- Phase 6: All admin content editing routes enforce strict locking rules: stem text is editable anytime; question/riddle options and answers lock once an attempt exists.
- Phase 6: Settings API checks phase boundaries and rejects modifications with `SETTING_LOCKED` when the event progresses past the specified lock point.
- Phase 6: Admin interventions (`admin_register`, `reset_attempts`, `set_captain`, `edit_team_n`, `set_qualified`) run atomically in Postgres (`005_phase6.sql`) and write to `admin_log`.
- Phase 6: Export endpoints serve UTF-8 CSVs for registrations, attempts, and standings with correct tie-break and rank computation.
- Phase 7: R1 answer submission (`submit_answer` kind 'r1') locks team row, enforces phase `r1_running` before deadline, validates option existence, checks max tries (`tries_r1`), awards `r1_points_per_riddle` on correct, and returns idempotent result via `attempt_result()`.
- Phase 7: `player_state` snapshot includes all riddles ordered by position with team attempt status (`open` | `correct` | `wrong`) during `r1_running` and `r1_closed` phases, and options are deterministically shuffled per team via `mapRiddleDTO` in `lib/state.ts`.
- Phase 7: Selection page (`/hq/selection`) dynamically calculates R1 standings rank with tie-breaks (points desc, earliest point-earning attempt asc), pre-identifies top N teams, and enforces qualification changes strictly in `r1_closed` phase.
- Phase 8: `claim_round3` enforces phase `r3_open`, checks `r3_eligible` team flag under lock, throttles wrong passwords per `password_max_wrong` and `password_lockout_s`, and guarantees exactly one winner via `insert into round3_claim (id, ...) values (1, ...) on conflict (id) do nothing`.
- Phase 8: Winner screen prominently displays team ID, winning room number, and secret key info; non-winners receive `ALREADY_CLAIMED` screen; spectators outside top 5 remain on spectator view.
- Phase 8: Admin panel features dedicated `/hq/round3` page with live winner banner enabling room organisers to verify team ID at the door against the database record.
- Phase 9: Hardening test suite (`tests/phase9_hardening.test.ts`) tests seeded shuffle determinism across distinct teams, point calculations for N in [3, 4, 5], question status transitions, rank tie-breaks, security sanitisation (no leaked keys or rooms), and Section 2.7 string normalisations. All 69 vitest unit tests passing.
- Phase 9: Load testing harness (`scripts/load-test.ts`) simulates 150 simultaneous participants polling `/api/state` with random jitter, tracking RPS, zero 5xx assertions, and p95 latency.
- Phase 9: Complete operations guide and one-page outage recovery policy documented in `README.md`.
- Phase 11 / UI Polish: Root layout in `app/layout.tsx` is neutral; player pages enforce `max-w-player` (480px) within their own page wrappers; `/hq` is wrapped by `Shell.tsx` (`app/hq/layout.tsx`) featuring a 240px fixed sidebar on desktop (>=1024px) and sticky top bar with slide-over drawer navigation on mobile (<1024px); dashboard renders a fluid responsive table on desktop and an optimized card-list on mobile screens with touch-friendly 44px+ targets.
